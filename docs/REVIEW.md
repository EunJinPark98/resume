## 2. 주요 결정

- **현대오토에버 전용 표현 제거.** 기존 사이트 히어로·About의 “현대오토에버에서 …” 문장을 모두 걷어내고, 울산 지역 어느 기업에도 쓸 수 있는 문장으로 바꿨습니다. 자기소개서의 “고향인 울산에 정착해 한 회사에서 오래 일하고 싶다”는 내용은 지역 기업이 가장 신경 쓰는 **장기 근속 의사**라서 연락처 섹션에 남겼습니다. 현재 울산에 산다고 읽히는 표현은 쓰지 않았습니다.
- **핵심 성과를 About보다 앞에 배치.** 요청된 기본 구조는 Hero → About → Achievements였지만, 채용담당자가 5초 안에 판단하려면 숫자가 히어로 바로 아래에 있어야 해서 순서를 바꿨습니다.
- **사례는 “요약 + Before/After + 결과”만 펼쳐 두고, 원인 분석·구현은 접어 둠.** 빠르게 훑는 사람과 면접관이 함께 읽을 수 있게 했습니다. 경력기술서 페이지와 PDF에서는 모두 펼쳐져 있습니다.
- **AI 활용은 역할을 나눠서 표기.** 별빛 초대장 상세에 “직접 수행 / AI 도구 활용”을 분리하고, “구현 코드의 많은 부분은 AI가 작성했다”고 명시했습니다. 대신 기획·요구사항·검토·테스트·배포·운영·보안 점검처럼 실제로 판단한 일을 구체적으로 적었습니다.
- **스크린샷이 없는 프로젝트는 실제 코드 구조로 그린 다이어그램 사용.** GREEN MOA(메시지 키 구조), 응애톡(처리 파이프라인)에 가짜 이미지 대신 넣었습니다.
- **기존 사이트에서 바로잡은 내용**
  - 경력 “2년 6개월” → 2023.12 기준 자동 계산 (현재 2년 11개월)
  - GREEN MOA 기간 2023.09–12 → 저장소 README 기준 2023.10–11 (개발 기간 23/10/04~23/11/10)
  - GREEN MOA 기술에 MyBatis·Spring Security·Thymeleaf·Oracle 추가 (`build.gradle` 기준)
  - 자격증 섹션에 정보처리기사 **필기 합격**을 취득 자격증과 분리해 표시
  - “24/7 미션 크리티컬” 등 근거를 대기 어려운 수식어 삭제
- **실제 측정하지 않은 수치 미기재.** IP 차단 사례는 차단 건수·성능 개선율 대신 설계상의 장단점(최대 1분 반영 지연)을 적었습니다.

## 3. 채용담당자 관점 검토

| # | 질문 | 평가 |
| --- | --- | --- |
| 1 | 5초 안에 어떤 개발자인지 이해되는가 | 히어로에 직무·한 줄 소개·현 직장·담당 업무·주력 기술·희망 근무가 모두 보이고, 바로 아래 성과 숫자가 이어집니다. |
| 2 | 3년 내외 경력직의 실무 경쟁력 | 대국민 서비스 운영 + 장애·데이터·보안 사례 5건이 문제→원인→해결→결과로 정리돼 있습니다. 경력 기간은 꾸미지 않고 “2년 11개월”로 표시됩니다. |
| 3 | 유지보수 인력이 아닌 문제 해결형인가 | 모든 사례가 “왜 반복되는가”에서 시작하고, 요청 없이 민원 유형을 정리한 일도 적었습니다. |
| 4 | 백엔드·프론트 역량이 모두 전달되는가 | Core(실무 Java/Spring/SQL)와 Project(React/Next.js/TS)를 표로 분리했습니다. 다만 **React는 업무 경험이 아니라 개인 프로젝트 경험**이라는 점이 그대로 드러납니다. 숨기지 않는 쪽이 면접에서 유리하다고 판단했습니다. |
| 5 | 울산 제조업 IT 기업에 매력적인가 | 운영 안정성·데이터 정합성·보안·사내 협업 체계(SVN) 경험은 업무시스템 운영과 직결됩니다. 제조 도메인 경험은 없으므로 만들지 않았고, 대신 장기 근속 의사를 전달합니다. |
| 6 | AI 활용이 신뢰를 떨어뜨리지 않는가 | 역할 분리 + 운영 중 보안 점검·데이터 보관 정책 같은 판단 사례를 함께 보여줘 “AI로 찍어낸 서비스”가 아니라 “AI를 써서 운영까지 해낸 서비스”로 읽히게 했습니다. |
| 7 | 프로젝트별 기여도가 명확한가 | 프로젝트마다 구성·역할을 표시했고, GREEN MOA는 커밋 이력으로 확인한 구현 범위만 적었습니다. |
| 8 | 면접에서 설명 못 할 과장은 없는가 | 아래 “확인 필요” 항목 외에는 원 자료에 있는 내용만 사용했습니다. 원인 분석 문장은 요청 본문의 설명을 풀어 쓴 것이므로, 면접 전에 실제 경험과 표현이 맞는지 한 번 읽어 보시길 권합니다. |
| 9 | 모바일에서 읽기 편한가 | iPhone 13 기준 가로 넘침 없음, 주요 버튼 높이 44px 이상(보조 링크 40px), 사례 전후 비교는 세로로 쌓입니다. |
| 10 | 연락·이력서 확인이 쉬운가 | 헤더(모든 페이지)·히어로·연락처에 PDF 다운로드, 이메일 복사 버튼, 경력기술서 웹 버전을 두었습니다. |

## 4. 검증 결과 (2026-11-09)

- `npm run build`: 타입 검사 통과, 6개 페이지 생성, 클라이언트 JS 2.6KB(gzip 1.2KB), CSS 약 31KB(gzip 7KB)
- `check-links`: 내부 링크·앵커·이미지 alt·h1 1개·중복 id 이상 없음. GitHub 링크 9개 모두 응답 200 (외부 도메인은 작업 환경에서 접속 불가로 미확인)
- axe-core (WCAG 2.1 AA + best practice): 6개 페이지 × 데스크톱/모바일 위반 0건
- Lighthouse (로컬 미리보기 서버, 압축·캐시 없음): 접근성·권장사항·SEO 100, 성능 93(홈, 모바일) / 98(홈, 데스크톱)
- 반응형: 1440px · 390px(iPhone 13)에서 전 페이지 가로 넘침 0, 콘솔 오류 0
- 키보드: 본문 바로가기, 모바일 메뉴 Esc로 닫힘 후 버튼으로 포커스 복귀, 사례 펼치기는 `<details>` 기본 동작
- PDF: A4 6쪽, 쪽 번호 포함
